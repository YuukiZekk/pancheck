# 反馈：缓存模式在真实库上的实测（2026-11-10）

测试对象：提交 6e73f68。数据：真实 dir_cache.sqlite 快照（229.6 万行）+ 真实 Emby 4.8.11 library.db 副本，
分区配置与金标准 CSV 模式一致。**sieve.py 仍逐字节未动。**

## 先说通过的

- **真库只读直连成功**，不用拷快照：open_mode = 只读直连，三区共读 219,471 行，全程 17 秒跑完，0 报错。
- 缓存时间范围有回显（time_min/max）；GHCR 镜像匿名拉取实测 200，amd64+arm64 都在。
- 结论：缓存读取层本身没问题，NAS 上部署不必担心那几百 MB 的拷贝。

## 三处口径差（模拟数据测不出来，真库才暴露）

### 1. 提取层没分离剧集文件 — 合集人口多了 2 万行

面板 heji_films 61,914 行 vs 金标准 42,495 行。路径集合对差（金标准 38,673 个唯一路径）：
交集 37,766；**面板独有 24,148，其中带集号标记的 20,619**；金标准独有仅 907；其余约 3.5k 是快照采样差。

手工流程在提取层就把带集号的文件单列（当时是 20,471 行），不进电影人口。面板把它们当电影行喂内核，
后果连锁：第三刀人口 11,015（金标准 9,308）、孤本 10,591（8,862）、守卫挂起 11,936（10,032）、分流桶 1,061 个夹（CSV 模式 134）。

改法：提取时按集号标记把文件行分流（和手工口径一致）— 带集号的行不进 heji_films，
直接归剧集分流（文件级，不是整夹）。分流的判定仍可保留文件夹级展示，但人口必须先分干净。

### 2. Emby 电影类型别靠猜 — 真库 Type=5 就是电影

真库 MediaItems 的 Type 分布：5 = 6,791（**与金标准电影数分毫不差**）、8 = 171,305（剧集单集）、
7 = 7,090、3 = 5,406（文件夹）等。面板的自适应类型判定输出 16,730 条 titles，多收近万条
（疑似把 7 等类型也算了电影），纵向随之漂移：入库提醒 22,732（金标准 21,021）、疑似 1,578（1,059）。

改法：Type 为整数且分布里存在 5 时，优先用「5 = 电影」的确定映射；自适应猜测只作兜底，
且猜测结果要在 probe 里显示出来让用户核对（现在用户看不到它猜了什么）。

### 3. emby_yp 按路径配对 — 在 strm 库上天然对不上

真库里 Emby 条目路径全在 `/CloudNAS/STRM/115/媒体库/...` 下（194,504 条），
`/CloudNAS/CloudDrive` 前缀下 0 条 — 这是 strm 镜像树，和库存路径（/115/01-好康的/...）不是一棵树。
面板「Emby 路径去前缀 = 库存路径」的假设在直挂库成立，在 strm 库不成立，yp 输出 0 行，
一刀参照档失去实测分辨率修正：A 504（金标准 553）、B 3,581（3,759）、D1 60（18）、E 110（72）。

真库本身不缺数据：MediaItems.Width 有值 17.4 万行，MediaStreams2 视频流带尺寸 176,703 行。
手工流程的解法是按 TMDB 键给分辨率（titles 表带 tmdb，分辨率按 tmdb 关联），原盘参照查不到路径时用 tmdb 兜底。

改法（任选其一，建议前者）：① emby_yp 改为按 TMDB 键输出，内核参照侧路径查不到时按同组 tmdb 查；
② 或在设置里明示「路径直配仅适用于直挂库」，strm 库自动降级并在结果页标注「分辨率修正未生效」。
无论哪种，别静默给 0 — probe 应显示 yp 命中条数。
